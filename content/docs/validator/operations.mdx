## Sign the vector

`chain.weights.set_weights` wraps the extrinsic with retries and checks the
permit before it signs anything.

```python
import bittensor as bt
from chain.weights import assert_validator_permit, set_weights

st = bt.Subtensor(network="finney")
wallet = bt.Wallet(name="pareton-validator", hotkey="default")
meta = st.metagraph(netuid=10)

assert_validator_permit(meta, wallet.hotkey.ss58_address, 10)

uids = [i for i, w in enumerate(vector.weights) if w > 0]
set_weights(
    st,
    wallet,
    meta,
    netuid=10,
    uids=uids,
    weights=[vector.weights[i] for i in uids],
    version_key=2032,
    burn_uid=201,
)
```

Call `assert_validator_permit` first. Without a permit the extrinsic fails as an
opaque substrate error, and this raises a message that names the problem
instead.

## The cadence

Recompute and set every 360 blocks, about 72 minutes. Read the head each pass
and compare against the block you last set at:

```python
head >= last_set_block + 360
```

Do not run it on a wall-clock timer. Blocks are the shared clock, and the decay
curve is measured in them.

Rebuild the vector on every cycle. The metagraph is authoritative each time. A
UID is a lease, not an identity: deregistration reassigns it, so a stored UID
eventually pays a stranger. Take `uid_count` from `len(metagraph.hotkeys)`, never
a hardcoded 256.

## Run it as a service

Keep the process supervised. A validator that stops setting weights stops
earning, and the chain does not warn you.

```ini
[Unit]
Description=Pareton validator weight setter
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=pareton
WorkingDirectory=/opt/pareton-validator
EnvironmentFile=/opt/pareton-validator/.env
ExecStart=/opt/pareton-validator/.venv/bin/python your_validator.py
Restart=always
RestartSec=30

[Install]
WantedBy=multi-user.target
```

## Commit-reveal

Subnet 10 runs with commit-reveal on. Your vector commits, and the chain reveals
it at the next epoch boundary.

A fresh commit is not readable on chain right away. Reading `Weights[10][<your
uid>]` immediately after a successful set correctly returns your previous
vector. The delay runs from near-zero to one full epoch, depending on where in
the epoch the commit landed.

This is not a fault, and it is the most common thing new operators report as a
bug. Wait a full epoch before you investigate.

```python
tempo  = st.query(("SubtensorModule", "Tempo"), [10])
reveal = st.query(("SubtensorModule", "RevealPeriodEpochs"), [10])
```

## Verify a set landed

```python
w = st.query(("SubtensorModule", "Weights"), [10, my_uid])
print(w.value)
```

You get a list of `(uid, u16_weight)` pairs. Values are quantized against a
ceiling of 65535, so they never match your floats exactly. Compare the ratio
between two UIDs rather than the absolute numbers.

Cross-check against Pareton at `GET /v1/weights`. The `breakdown` carries the
`blocks_held` each weight was computed at, so a difference is usually the clock
rather than a disagreement. Compare at the same `computed_at_block`.

## Failures worth reading

| Symptom                                  | Cause                                                    |
| ---------------------------------------- | -------------------------------------------------------- |
| `holds no validator permit`              | Your stake is not high enough to keep a permit           |
| `is not registered on netuid 10`         | The hotkey lost its UID                                  |
| `burn_uid is outside the metagraph`      | `uid_count` is wrong; read it from the live metagraph    |
| Chain shows the old vector after a set   | Commit-reveal delay. Wait one epoch                      |
| Your vector disagrees with `/v1/weights` | Different `computed_at_block`. Compare at the same block |
| Other validators do not trust-weight you | `version_key` does not match                             |

## Keep your version key aligned

`version_key` is 2032. It tags the mechanism version your vector was computed
under. Validators trust-weight each other only while their keys agree, so a bump
is a coordinated announcement across operators, never a value you choose or a
deploy artifact. Read the current key from `GET /v1/weights` and match it.
